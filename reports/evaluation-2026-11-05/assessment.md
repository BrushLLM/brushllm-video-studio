**BrushLLM Video Studio v0.0.7：功能、界面与性能评估**

评估日期为 2026-11-05（北京时间），代码基线为 `de6368e`。后续改动见[修复记录](../fixes-2026-11-05/fix-notes.md)。

结论：项目已有清晰的分层、较完整的媒体工具覆盖、可靠的输出文件保护，以及实际可用的硬件编码性能。不过，默认音频转换不可提交、用户选择的 AV1 被替换为 VP9、旧编码字幕缺少操作入口，说明关键用户流程仍有缺口。建议先修复这些问题，再将其定位为稳定正式版。当前更适合作为持续完善的早期桌面工具。

| 维度 | 评价 | 主要依据 |
| --- | --- | --- |
| 功能 | 覆盖较广，关键流程有阻断 | 26 个工具；发现默认音频转换阻断、编码选择未生效、字幕编码入口缺失 |
| 界面 | 视觉体系统一，操作反馈与信息可信度待提高 | 语义色、深浅主题、错误详情、自动滚动较完整；预估与实际不一致、缺少画面预览、跨页配置丢失 |
| 性能 | 本机单任务编码表现良好，批量资源治理不足 | VideoToolbox 有明显速度优势；探测不限并发、重复探测、同步采样与全量列表更新存在风险 |

本轮方法与边界：阅读当前源码及测试；使用刚完成的 254 项测试和生产构建结果；启动源码对应的 Electron 应用并检查空态；通过同一 React 渲染层的浏览器预览检查视频、音频与字幕参数流程；使用真实 FFmpeg/ffprobe 验证编码、压缩及字幕预处理；执行项目自带基准和额外诊断。浏览器截图中的媒体数据来自 mock，仅用于说明控件和校验行为，不能作为真实媒体数据。本轮未完成完整原生文件选择到导出的 GUI 链路、Windows 实机验收、全九语言视觉验收、4K/HDR/长片和冷启动/峰值内存专项测量。

**功能方面的已确认问题**

1. **P1：音频转换的默认设置无法提交。** 添加音频后选择格式转换，采样率和声道均默认“原始（直接流复制）”，加入队列按钮禁用，并显示“无效的采样率”。`src/ops.js:158` 将这两个默认值设为字符串 `0`，`engineParams` 转为数字 0，`shared/validation.mjs:51`、`:52` 将其判为非法；这是 UI 和共享校验共同复现的结果。手动将两项改为 48000 Hz、2 声道后，按钮恢复可用。建议使用统一的“沿用源值”语义，在进入校验前剔除未指定参数；补充覆盖默认界面参数的测试。

2. **P1：WebM + AV1 实际输出 VP9，任务仍显示成功。** 用真实 JobManager 和 FFmpeg 执行视频转换，结果为 `requested=av1, resolved=av1, plan=AV1, actual=VP9, status=done`。`shared/resolve.mjs:20` 允许 WebM 使用 AV1，但 `electron/engine/commands.js:189` 无条件改为 VP9；输出验证目前没有发现视频编码与请求不符。建议以解析后的编码结果为唯一执行依据，并核对实际编码。修复前应暂时限制该组合，避免向用户显示错误承诺。

3. **P1：GBK 等旧编码字幕的烧录、封装流程缺少源编码选项。** `prepareInputs` 在检测到旧编码歧义时要求显式 `sourceCharset`。实测 GBK SRT 不传该参数会报 `SUBTITLE_CHARSET_AMBIGUOUS`，传 `gbk` 可成功完成准备。源编码控件却只在三个即时字幕工具中出现（`ToolPage.jsx:290`），烧录和封装操作没有入口，也未把该状态加入任务参数。用户只能先转成 UTF-8 再操作。建议在副字幕输入处增加编码选择，并允许每个文件单独设置或明确统一设置的范围。

4. **P2：输出计划与执行使用了不同的判断规则。** 已通过诊断确认：WebM 缩放的计划仍显示 WebM，而输出扩展名为 `.mp4`；同编码但不同尺寸的视频自动合并，计划显示 `stream copy`，执行则使用重编码过滤器。另有 MP3 裁切预估容器显示 MP4 的情况。根因包括 `shared/plan.mjs:417` 自行推断容器、`:120` 仅比较编码名，而执行层使用更完整的兼容性规则。建议复用 `shared/media.cjs` 的容器及合并判断，让计划、命令、实际输出共享同一份决策。

5. **P2：默认 GPU“压缩”可能明显增大低码率素材。** 640×360、6 秒样例从 501,857 字节变为 936,972 字节，增大 86.7%。自动 GPU 码率按分辨率及预设计算，并设有 1500 kbps 下限（`shared/resolve.mjs:25`），没有结合源视频码率或目标体积。编码器通常无法保证每个素材都变小，但压缩工具应识别这种情况，给出警示、按源码率约束或提供目标体积选项，不应默认让用户把增大的文件当作成功压缩。

6. **P2：输出位置的文案可能误导。** 代码确认：未在当前页选择目录时，界面固定显示“与源文件同目录”（`ToolPage.jsx:343`）；主进程却优先使用设置中的全局输出目录（`electron/main.js:133`）。这是静态确认，未在本轮修改用户的全局设置。建议展示完整的有效输出位置及来源，区分全局设置、本次指定、源目录，并提供恢复源目录的明确入口。

功能优势也比较明确：工具注册表驱动通用参数面板，视频/音频/字幕分区清楚；暂停、取消、重试和并发队列已实现；处理完成后重新探测输出；输出通过临时目录、重名分配和文件身份校验保护；ASS/SSA 样式保留、字幕歧义检测较谨慎。这些机制值得保留。本地处理无需上传媒体，检查更新属于用户主动发起的网络功能。

工具边界应保持明确：当前是媒体处理工具箱，缺少时间线、画面预览、字幕识别等能力。时间线和 AI 不必作为当前版本的必需项；优先补齐裁切、裁剪和烧录操作所需的轻量预览更实际。README 宣称 33 项操作，注册表实际为视频 12、音频 8、字幕 6，共 26 项，建议统一口径。

**界面方面的评估**

视觉基础较好：字体、间距、圆角、主按钮和领域色形成统一体系；深浅主题采用语义变量；工具选中后已自动滚动到配置区；错误信息有摘要与可展开详情；空队列提供操作入口；弹窗具备焦点管理。这些是当前代码中的实际实现，旧报告中的“完全不滚动”“错误仅显示原文”等问题不能再直接计为缺陷。

主要改善方向：

- **降低页面往返成本。** 文件区、全部工具卡、参数、输出预估、提交按钮构成长页面。默认 1240×820 窗口下，视频工具首屏只展示部分分组。自动滚动缓解了找参数的问题，但切换工具仍需返回上方。建议使用可持续访问的工具选择区，或将工具列表与配置区并排，并在小窗口采用紧凑布局；主操作条可固定在当前配置区底部。
- **保留配置上下文。** 浏览器实测，从视频转换切到其他页面再返回，文件保留，但选中工具和参数被重置；原因是 `ToolPage` 的配置只存在局部状态。建议像文件列表一样按页面保存配置草稿，至少保留选中工具、参数、副输入和输出目录。
- **提供轻量画面预览。** 目前裁切依靠时间数值、裁剪依靠尺寸和偏移、字幕烧录依靠字号与边距，缺少直接验证效果的画面。建议先提供抽帧预览、时间点预览、裁剪矩形和字幕示例，不必一次引入完整编辑器。
- **改善处理中反馈。** 非即时任务的 `submit` 没有提交中状态或防重复机制，IPC 在准备整批文件期间按钮保持可点击；建议立即显示“正在准备 N 个文件”、禁止重复提交，并支持取消准备。探测失败后也没有显式重试入口，只能移除再添加。
- **提高信息可信度。** 修复上述预估、编码和目录问题比继续调整颜色和阴影更重要。“原始（直接流复制）”用于采样率/声道容易让用户误解整个格式转换不会重编码，应改为“沿用源采样率/声道”。

**性能实测与判断**

机器：Apple M4、10 个逻辑 CPU、16 GiB 内存、macOS arm64。使用项目自带的 FFmpeg 6.0。输入是合成的 10 秒 1920×1080、24 fps、带 AAC 音轨视频。每个场景预热一次，再测三次；表中为耗时、体积和 PSNR 中位数。桌面同时有其他应用运行，结果适合作为本机对照。

| 场景 | 耗时中位数 | 输出体积 MiB | PSNR dB |
| --- | ---: | ---: | ---: |
| CPU H.264 medium，CRF 23 | 4.256 秒 | 6.52 | 45.59 |
| CPU H.264 fast，CRF 23 | 4.224 秒 | 6.56 | 45.47 |
| VideoToolbox H.264，平衡预设 | 1.723 秒 | 6.14 | 42.93 |
| VideoToolbox H.265，小体积预设 | 1.889 秒 | 4.38 | 40.66 |
| CPU H.264，5000 kbps | 2.309 秒 | 6.22 | 44.69 |

H.264 硬件方案相对 CPU fast 在此样例中快约 2.45 倍。但 GPU 与 CPU 使用不同的码率/质量策略，PSNR 也有差异，不能把该数字解释为同画质下的加速。CPU fast 与 medium 的中位数仅差 0.8%，三次运行有明显波动，本轮不足以支持“fast 显著更快”。PSNR 只用于当前合成素材的客观对照，不能替代真实内容的主观画质验收。

项目基准本轮通过全部门槛。现有基准只覆盖短时合成素材和少数转码组合，应增加真实运动画面、屏幕录制、低码率素材、4K/HDR、多声轨及不同长度样例；GPU 检测到编码器名称也不等于所有设备上的运行时可用性，现有回退机制仍需平台验证。

| 性能项 | 发现与影响 | 建议 |
| --- | --- | --- |
| 文件探测并发 | `ToolPage.jsx:66` 对全部文件直接启动异步探测，无上限 | 使用共享的有界探测队列，并支持取消 |
| 批量准备 | 导入、IPC 提交、任务执行都会探测；IPC 提交逐个串行探测整批后才入队 | 缓存带路径、大小、修改时间的探测结果；执行前核验有效性；分块提交并报告准备进度 |
| 主进程同步操作 | CPU 采样在主进程使用 `spawnSync`；Windows 暂停恢复也同步启动 PowerShell | 改为异步进程或专用采样服务，避免阻塞 IPC；Windows 延迟需实机测量 |
| 多任务资源分配 | 每个 FFmpeg 都自动使用线程；同时运行最多四个任务，没有统一 CPU/内存预算 | 保留保守默认并发，增加按任务与机器能力分配资源的策略 |
| 队列渲染 | App 与 QueuePage 重复订阅更新；每次更新查找并复制数组，所有任务卡均渲染 | 合并订阅、规范化状态、任务卡 memo 化；大量历史任务时分页或虚拟列表 |
| 队列持久化 | JobManager 仅保存于内存，退出取消任务；没有恢复机制 | 保存待处理任务与历史，明确区分重新执行与断点续编码 |

额外做了 40 次相同本地短文件探测：并发 4 耗时 102 ms，并发 40 耗时 71 ms。该样例没有体现出限流后的速度优势，因此不能宣称当前探测已经造成明显卡顿；上述建议针对大文件、慢盘、网络目录和资源峰值的可控性。未对这些场景做实测。

本地现有 macOS v0.0.7 安装包为 132.1 MiB，安装目录约 444.7 MiB，其中 `app.asar` 约 0.6 MiB，解包媒体引擎约 60.8 MiB。体积主要来自 Electron 运行时及媒体引擎，前端业务包不是主要来源。此处测量的是现有发布产物，不代表已重新打包或验收全部安装器。

**修复顺序与验收建议**

第一批：修复默认音频转换、WebM AV1、字幕源编码入口，增加真实用户流程回归。验收应包括：导入一个有效音频后不改参数即可加入队列；选择 AV1 后产物 ffprobe 确认为 AV1；GBK 字幕能在烧录/封装页面直接指定编码完成处理。

第二批：统一预估与执行决策，显示真实输出目录，为压缩后可能增大提供明确反馈，防重复提交并保存配置草稿。验收矩阵包含 WebM 编辑转 MP4、不同尺寸自动合并、全局输出目录和低码率素材压缩。

第三批：探测队列与缓存、异步 CPU 采样、大队列渲染优化、任务持久化，以及轻量画面预览。先量化 100/1000 文件导入与队列更新、主进程事件循环延迟，再判断优化效果。

现有 254/254 测试通过、生产构建通过，是工程基础的正面信号。不过 E2E 当前主要从 JobManager/引擎入口执行，无法替代默认 UI 参数→校验→IPC→真实输出的用户流程验收。本轮发现的音频默认值问题正好说明这一覆盖缺口。建议将几条核心 GUI 流程纳入发版门槛，再做完整 Windows x64/ARM64 实机验收。

原始数据见 [benchmark.json](benchmark.json)、[functional-results.jsonl](functional-results.jsonl) 和 [load-results.jsonl](load-results.jsonl)。
